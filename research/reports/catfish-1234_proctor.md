# catfish-1234_proctor

Paths without a prefix are in `other-solutions/catfish-1234_proctor/`. `fw:` means `agentic-framework/`.

## 1. What it really is

- A single-purpose TypeScript/Node diff checker for test tampering, not a framework. It has no tickets, lifecycle or agent workflow. 14.5k lines of `src`, 15.3k lines of tests (about 1,220 test cases by grep), 408 commits from 2026-07-01 to 2026-11-03, one main author, v1.2.2 (VERIFIED).
- Pipeline: `git diff` -> pre-classifier -> 27 regex/structure verifiers (14 RH, 13 WI; 20 on by default) -> findings -> exit code. It ships a CLI, a git pre-commit hook, a Claude Stop hook, a GitHub Action with SARIF, 30 ruleset file targets, an opt-in Linux-only dynamic test runner, and a two-arm agent benchmark (VERIFIED).
- It works as described, and its README is unusually honest: it says defaults miss about half of its development cheats and the live benchmark shows no effect. Static mechanics were read, not run (brief forbids executing it).
- Claims the code does not support:
  - `src/skill/SKILL.md:74-76` says the guard "stops the commit or turn" and there is "no way to reason around it". The Stop hook skips when `stop_hook_active` is true (`src/hooks/stop-hook.ts:20`, `src/cli.ts:299`), so a second stop passes, and it fails open (`:65`).
  - "A change cannot approve itself" holds per commit and in CI `--base`. Locally, commit 1 can add an approval and commit 2 can use it, and WI104, which flags that, is not on by default (`src/context/index.ts:128`).
  - `normalizeConfig` says a blanket mute "must not" be possible, but `src/engine.ts:123` applies `file` as a glob, so `"file": "**"` passes validation (no check rejects it; INFERRED from reading, not run).
  - Stale numbers: README says 5/72 benign flagged, CHANGELOG 1.2.2 says 3/72. `src/context/index.ts:116` still cites the 689-commit sweep that `docs/BENCHMARKS.md` retracts.

## 3. Challenges

- **"Agents forge evidence, so hooks must stop them."** Proctor is the best local test of this and gets no effect: 44 live invocations, 1 flagged per arm, and that one was a false positive. All 44 passed held-out tests, including 7 tasks built so cheating was cheaper (`bench/results-live.csv`, VERIFIED count; `docs/BENCHMARKS.md`). Verdict: the framework's adversarial stance is not disproved (one agent, 22 small synthetic tasks, ruleset only). But spending most of the design on a dishonest agent is unsupported. Its own cited paper rate is far higher on ambiguous tasks than clear ones (repo's citation, not checked). If so, ambiguity control (interview, Done Contract) may pay more than anti-forgery. Keep forgery guards cheap, and measure.
- **Review limited to changed lines.** Proctor's diff-only checks hit a stated ceiling: defaults caught 35/72, and misses are mostly things that need execution (`docs/BENCHMARKS.md`). Its unfixed false positives are cases a diff cannot decide (`bench/heldout/README.md`). Verdict: the framework is right to spend on a critic, wrong to drop findings outside the changed lines. A defect in an unchanged caller is exactly what diff-bound logic cannot see.
- **A selftest as the main proof.** Contradicted, and proctor is right. With all checks on, its fixtures score 139/139 while the held-out cases, once blind, scored 42/72 (`docs/BENCHMARKS.md`). The gap is the value of a separate evaluation. The framework's 210 checks are the equivalent of the 139.
- **Bash plus files as the runtime.** Partly contradicted. TypeScript buys structured diff parsing, a typed verifier API and Windows support, at the cost of a Node dependency. Verdict: for a state machine, bash is fine. For content analysis it has hit its limit, and floor-guard is already python in a heredoc. Move analysis to a real language or an external tool, keep the railroad thin.
- **One hook set for three tools.** Proctor uses less per-tool hooking and leans on git hooks and CI, with a Stop hook for Claude and Cursor. Verdict: proctor's layering is more portable: git and CI first, tool hooks as earlier feedback only.
- **Copy-in distribution.** Contradicted. npm, plugin, extensions and `setup` with a manifest is better for clean templates. Proctor's dependency on npm is not needed; a release tarball with an install script would do (ASSUMED).
- **A human accepting every ticket.** Proctor's approval is narrower: humans approve the exception, nothing else needs acceptance. Verdict: for orchestration this is the better default. Gate only by risk, and make an exception a committed, reasoned, baseline-read record.
- **Long AGENTS.md.** Proctor's 154-line ruleset is similar in spirit, but a live run showed it changed nothing measurable. Weak evidence that prose adds little beyond the enforced parts.
- **Where the framework is right:** `floor_exceptions` carry an expiry, while proctor approvals never expire and bind only rule plus file. A dated exception is better.

## 4. Delete or simplify

- Delete floor-guard's own stub, skip and assertion regexes if the external-checker slot lands. Keep only what is framework-specific (thresholds in `config.yml`).
- Remove the `floor_ignore` entry for `scripts/floor-guard.sh` and `scripts/selftest.sh`. Exempting the guard from its own scan means tampering there goes unscanned. Proctor blanks comments and literals instead of exempting its own source.
- Replace `test_ratchet` (`fw:scripts/gate.sh:681`), which mostly no-ops, with the base-tests run above, or delete it.
- Replace `Ruling:` grep in the ticket (`fw:scripts/gate.sh` `test_ratchet`). It is agent-writable, so it proves nothing unless read from the baseline.
- Fewer settings. Proctor's config has 9 fields. Each framework option whose value is "off" at CI time is a hole unless read from the baseline.

## 5. Orchestration

- Proctor is a good leaf component: stateless, works on a ref range, needs no ticket, offline, and gives the same answer on any clone. The framework should expose the same shape: a pure `gate verify-range --base X --head Y --json` that any orchestrator can call, separate from the railroad.
- `src/score.ts:9-14`: history is recomputed from git rather than kept in a log, so there is "no state to corrupt". Each past commit is judged by the config at that commit (`:88-90`). Apply to shared-clone problems: derive status from refs and commits, not gitignored `.agentic/state/`.
- Local tally goes in `.git/` (`src/session.ts:5-9`) so it never shows in a diff, and it is cosmetic. Clear split: durable truth in git, disposable state elsewhere.
- Explicit fail policy per surface: pre-commit fails closed, Stop fails open so an agent is not wedged, CI is the authority (`README`, "Can the agent get around it?"). The framework should state this per hook. An orchestrator needs to know which signals are authoritative.
- Midway-state handling: skip when `MERGE_HEAD`, rebase or cherry-pick markers exist (`src/hooks/stop-hook.ts:79-91`), so another branch's changes are not blamed on the agent. Relevant to `advance` under automated merges.
- Unattended mode: approval is one committed record with a reason, so an orchestrator identity could write it to base. Proctor does not implement identity. Note the friction: with config read from base, a legitimate test removal in a PR needs its approval merged first (INFERRED from `action.yml` plus `src/cli.ts:181`).

## 6. Do not copy

- **The rule tower.** `rh002.ts` is 1,155 lines of per-language tables, some marked "MEDIUM confidence, from training knowledge". A long chain of regex rounds (`bench/redteam/README.md`: 11 rounds, from 4/20 to 76/76) is corpus tuning. Default catch on the set not tuned against stayed about half.
- **Reporting tuned sets as headline numbers.** They label them correctly now, but the README still opens with 139/139. Keep frozen sets frozen.
- **"30 agents supported".** Almost all of those are a copied rules file. `setup` writes a Stop hook only for Claude, and the plugins add one for Claude and Cursor (`plugin/hooks/`). Say what enforcement each tool really has.
- **"Honest pass" and the badge.** A warn-only run is `honest-pass` (`src/receipt.ts:25`). README itself says clean means only "nothing matched a known pattern". Naming should not overclaim.
- **Agent-writable excuses.** `hasExplanation` lets an added comment silence findings (`rh002.ts:806`, `rh003.ts:731`). RH006 accepts a keyword in the commit message (`rh006.ts:31`). Both contradict the "marker must predate the change" rule at `src/engine.ts:78`.
- **`npx --yes` in a commit hook** (`src/hooks/pre-commit.ts:38`). Unpinned code fetched at commit time. Prefer a pinned local install and fail closed.
- **JSON output as is.** `src/reporters/json.ts:3-5` emits a bare findings array: no schema version, no verdict, no ran/skipped status. Exit 2 also covers invalid arguments (`src/cli.ts:90,133`), so a finding and a usage error collide. Exit 1 is both warnings and some argument errors.
- **Skip equals pass in dynamic checks.** `dynamic: skipped` adds nothing (macOS, Windows, no `bwrap`). If the framework runs tests, a skip must be visible in the verdict.
- **Tests that grep prose** (`tests/readme.test.ts`, `tests/release-hardening.test.ts`). They mostly pin wording.
- **Rules in text with no ground truth.** `SKILL.md` claims guard coverage that is opt-in or fail-open.
- **History:** many one-file "Bump version" commits and several "stray upload" removals, from web-UI editing. Nothing suspicious was found in the skill, commands or recipe; `recipes/proctor.yaml` tells agents not to self-approve, which is good. No prompt-injection text noticed in the files read.

## 7. If you rebuilt the framework

Keep the railroad idea: one command, a first-match table, scripts own state. Change its evidence model. Every gate becomes a pure function of a commit range plus a baseline-read policy, returning a versioned JSON verdict with distinct passed, failed, could-not-run and skipped states. CI re-derives everything and is the only authority; local hooks (git first, tool hooks second) are fast feedback with a declared fail policy. Exceptions are dated, reasoned, read from the baseline, and stay visible. Content analysis moves out of bash behind a pluggable checker slot, and proctor fits that slot. Add `evals/`: a pinned real-commit precision sample, a frozen cheat set, and a two-arm held-out benchmark that measures outcome, cost and time, with a rule or a ceremony step kept only if it earns its place.
