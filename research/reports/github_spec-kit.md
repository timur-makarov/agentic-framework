# github/spec-kit

Paths are relative to the clone unless they start with `fw:` (`agentic-framework/`). License: MIT (`LICENSE`, and the `github/spec-kit` row in `MANIFEST.tsv`), so code may be copied with the notice kept. All Take items are ideas first. The code is Python and tied to its own package.

## 1. What it really is

A mature, very active Python CLI (`specify-cli` 1.3.2.dev0, 2,364 commits since 2025-08, 79K lines in `src/`, about 7,350 test functions, 44 integration directories). It installs prompt templates and small scripts into a project for many coding agents, and manages them afterwards. It has two separate halves. The **process** half is prompts: 9 command templates, 132 KB. They drive spec, plan, tasks, implement, converge. The **platform** half is an installer, a package system (extensions, presets, bundles, catalogs, auth) and a YAML workflow engine.

Almost all its engineering goes into distribution and composition, and almost none into enforcement. Core ships no guard hook, and nothing verifies that a step's work happened (VERIFIED: no shipped `extension.yml` declares `events:`; `command` step success is exit code 0, `workflows/step/command/__init__.py:216-233`).

README claims the code does not support:
- "Enforce organizational or regulatory standards" via Preset (`README.md:50`). Presets are template text resolved by priority (`presets/_resolver.py:15-23`). Nothing enforces them.
- `spec-driven.md:312` calls test-first "NON-NEGOTIABLE", while the shipped `templates/tasks-template.md:12` says "Tests are OPTIONAL". The "nine articles" are not in the shipped constitution template, where Test-First is only an example comment (`templates/constitution-template.md:17`); `plan-template.md:43` has a placeholder for gates.
- `design/mcp.md:101` says a generic `specify_run_command` is not part of the architecture, but `mcp_server/server.py:79` registers one. It accepts only `version`, so the harm is small. The MCP server is labeled experimental, and only `workflow.list` has `disposition="available"` in the workflow inventory (`workflows/_mcp.py:123`).
- No outcome evidence: I found no eval or benchmark of SDD results in docs, newsletters or `spec-driven.md` (VERIFIED by grep).

## 3. Challenges

- **Scripts own state, prose owns judgment (framework) vs prompts own process (spec-kit).** Framework is right, and spec-kit is the best evidence. "Mandatory" hooks are text the agent must act on, with the prompt pleading "Emitting the block alone does not run the hook" in all 9 templates. `HookExecutor.execute_hook` only returns data: "The actual execution is delegated to the AI agent" (`extensions/__init__.py:6174-6179`). The community catalog then rebuilt enforcement from outside: `gates`, `ci-guard`, `verify-tasks` ("phantom completions"), `vurnix`. 191 community extensions, many of them gates, show where the unmet demand is (INFERRED). Keep this premise. It is the framework's differentiator.
- **Copy-in.** Spec-kit is right. An installer with manifest and upgrade is table stakes for "ready to use". The framework does not need PyPI to get it.
- **Bash plus files as runtime.** Partly wrong. Spec-kit started with bash, then added Python ports (#3386, 2026-07) and now carries three script languages with parity tests (`tests/test_create_new_feature_python_parity.py`, 1,789 lines). The framework already requires python3 and parses YAML with awk. Verdict: move `gate.sh` and `lib.sh` to single-language stdlib Python with no packages. Keep files and git as the store. Do not take spec-kit's dependency list. Note one lesson: its generated dispatcher has an inline stdlib fallback because a `uvx` run leaves no CLI behind (`events/__init__.py:97`). Hooks must run with only what is in the repo.
- **Tickets vs feature folders (spec, plan, tasks).** Keep tickets. Spec-kit needs at least 5 commands and several documents per feature, and its own `presets/lean` cuts prompts to 3.7 KB (5 files) from the 132 KB core set, which suggests the full path is heavy (INFERRED). Useful addition: stable item IDs in the Done Contract, so findings can cite `source-ref`.
- **Three risk lanes.** Spec-kit has no risk concept. Every feature takes one path, and the alternatives are other processes (`bug`, `assess`, `lean`). The framework's lanes are better because they tie cost to risk. But spec-kit's framing, "independent entry points, not mandatory phases" (`README.md`), is a useful correction: bug fix and idea assessment should not need the same ticket template.
- **Review limited to changed lines.** Spec-kit contradicts it, and is right about intent gaps. The framework is right that a reviewer needs bounds. Verdict: keep citations required, but allow a citation to any file or a contract item, not only an added line.
- **A human accepts every ticket.** Neither is right alone. Spec-kit's slash flow has no acceptance at all; gates are optional per workflow. Its `bug-fix.md` shows the good form: a human act on the platform (a label), which the agent's token cannot perform. Verdict: acceptance is policy per tier, recorded by an identity the agent lacks.
- **One hook set for three tools.** Spec-kit supports the premise: canonical events, one dispatcher, a `CANONICAL_TO_NATIVE` table per agent (`integrations/claude/__init__.py:58`). It differs in using a neutral schema; the framework uses Cursor's as canonical and hand-codes `adapt.sh` cases. Prefer a neutral schema and a data table. Spec-kit's mapping says nothing about tool-matcher coverage, so it does not help with Grep/Glob or `python -c`.
- **18 skills.** Spec-kit has 9 core and puts everything else behind opt-in packs. Direction right: split a core railroad from optional craft skills. The pack system is not needed; a directory and a flag are enough.
- **Long AGENTS.md.** Spec-kit's is 3.7 KB, mostly "before changing X, read Y". It is for contributors, so the comparison is limited. The router form is still worth adopting.
- **Selftest as main proof.** Same blind spot at 350 times the test count. CONTRIBUTING scopes required testing to behavior "without an LLM". `tests/hooks/` holds only manual markdown. Nothing here shows either approach improves outcomes, so spec-kit offers no eval method to copy.

## 4. Delete or simplify

- Do not grow toward packages. Extensions, presets, bundles, catalogs and overlays are five composition mechanisms for one need. A project override directory covers it.
- Shrink `adapt.sh` tool branches to a table plus a neutral payload.
- Move `agentic-api`, `agentic-migrate`, `agentic-idea` and similar out of the default set into an optional folder. Keep lane skills only.
- Replace the many-section `ticket-full.md` with a lean default, then test what is lost. `presets/lean` shows how small a working prompt can be, though no data shows it performs as well.
- Trim AGENTS.md to rules and routing, and leave `judgment.md` on demand.
- Delete `tracker` and `models.*` until applied. Spec-kit's `model` field works only because a dispatcher consumes it (`step/command/__init__.py:353`).

## 5. Orchestration

**Inside an orchestrator.** Spec-kit shows the minimum surface: start with a caller-supplied id, one JSON outcome, a gate payload, resume with inputs, exit codes that map to terminal states, and paused as a non-error (`_commands.py:1071`). Copy that. Its explicit CLI inventory records for each command a disposition, capabilities (`local-read/project-write/execution/self-modifying`) and network access (`workflows/_mcp.py:34-52`). A one-page version of that table for `gate.sh` is worth having, because an orchestrator can then allow reads and hold writes. Do this before any MCP server. Spec-kit's own MCP has shipped little since 2026-10, and JSON CLI covers the need.

**As an orchestrator.** The engine has useful step types (`command`, `shell`, `gate`, `if`, `switch`, `while`, `do-while`, `fan-out`, `fan-in`, nested `workflow`) with atomic checkpoints (`engine.py:808-878`). It is still an in-process runner for one checkout. No workflow code mentions worktrees, so concurrent `fan-out` agents share a working tree (VERIFIED by grep). The run lock is a thread lock (`engine.py:743`). There is no queue, daemon, or cross-clone state, and agent exit 0 counts as success. Treat it as evidence of what a linear runner needs, not as a design for parallel agents. The framework's per-ticket branch, frozen scope and overlap refusal are stronger for parallel work.

**Standalone.** `specify init`, then a slash command, works with no extra concepts. The framework should match this with one install command and a working first ticket.

## 6. Do not copy

- **Size.** `extensions/__init__.py` is 6,235 lines, and 663 of 2,364 commits start with `fix`. Much of the code is defense against states its own flexibility created. `gate/__init__.py` holds long comments for bugs like an interrupted prompt counting as approval (#4529, fixed `options[-1]` reject assumption).
- **Hooks that do not run.** Templates tell agents to skip any hook with a `condition` and "leave condition evaluation to the HookExecutor" (`templates/commands/analyze.md:26`). `check_hooks_for_event` is the only caller of `should_execute_hook`, and nothing in `src`, `templates`, `scripts` or `extensions` calls it (VERIFIED by grep; tests not checked). So in the slash flow a conditional hook is silently skipped. Also, unparseable `extensions.yml` means warn and "continue normally", even for mandatory hooks.
- **Gates that prove nothing.** No actor is recorded. `state.json` is only shape-checked on load (`engine.py:881`), and an agent can run `workflow resume --input verdict=approve`. A local overlay can `replace` a gate (`docs/workflows/overlays.md`). This has the same weakness as the framework's critic gap, so take the interface and not the trust model.
- **Fail-open dispatch.** A missing event command exits 0 (`events/__init__.py:296`). Fine for lifecycle events, wrong for a guard. Keep the framework's fail-closed PreToolUse (`fw:scripts/hooks/adapt.sh:8`).
- **Default all-permissions dispatch.** Copilot gets `--yolo` by default (`integrations/copilot/__init__.py:347-356`). Shell steps use `shell=True` with strict mode opt-in (`workflows/step/shell/__init__.py`).
- **Open catalogs.** 191 community entries; catalog digests are optional and "Entries without a declared digest are accepted unchanged" (`shared_infra.py:48-58`). The README itself says listings are not audits.
- **Three script languages, 44 agents.** Each adds a permanent parity cost. `CHANGELOG.md` is full of per-agent flag fixes.
- **Spec-as-source-of-truth rhetoric.** `spec-driven.md` makes broad claims (for example, constraints discovered "automatically", `:25`) with no supporting code or measurements.
- **Suspicious content.** None seen in what I read. `AGENTS.md` and `CONTRIBUTING.md` address agents as contributors (trailers, PR caps). I treated these as data and did not follow them.

## 7. If you rebuilt the framework

Keep the core idea exactly: one next-move decision table, scripts own state, hooks guard, judgment in prose, tickets on branches, risk lanes. Rebuild the shell around it the way spec-kit built its installer: stdlib Python, everything under `.agentic/`, a hash manifest with `install`, `upgrade`, `uninstall`, marker-owned merges into each agent's config, and an allowlisted payload with a test that a fresh project contains no template history. Give every command a JSON outcome with an id, status, `who`, and distinct exit codes, plus a capability table. Make acceptance and reviewer proof events from an identity the agent does not hold, enforced in CI against the claim commit. Widen review from diff to contract using gap types. Refuse everything else spec-kit has built: no catalogs, presets, bundles, workflow YAML or MCP until someone needs them.
