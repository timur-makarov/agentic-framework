## 1. What it really is

A hosted GitHub bot, not a framework. A Vercel webhook routes GitHub events, starts a run on Warp's proprietary Oz cloud, stores `RunState` in Vercel KV, and a one-minute cron collects the run's JSON artifact and applies it to GitHub (VERIFIED: `api/webhook.py`, `core/dispatch.py`, `core/poll_runs.py`, `vercel.json`).
Size: about 16,500 lines of Python in `core/`, `oz/`, `api/`, `.agents/`; 11,800 lines of tests (513 `def test_`, not run); 16 `SKILL.md` files; no `AGENTS.md`; no hooks. 273 commits from 2026-03-17 to 2026-09-08, at least 129 by bot accounts, dogfooded on itself. It looks wound down: the README points to Warp Factories and `core/routing.py:125-126` says "remove once oz-for-oss is retired".
It is mature in the sense of being real production plumbing with scars. It is not "reusable" as the README says: it cannot run without Oz, needs external `warpdotdev/common-skills` (`core/skills.py:9-18`), and hardcodes Warp repos (`core/routing.py:127-130`, `oz/ownership.py:37`).
Claims the code does not support (VERIFIED):
- `update-*` skills say a "self-improvement runner enforces" the write surface, but `maybe_push_update_branch` has no caller. The entrypoints (`.github/scripts/update_*.py`) were deleted in 6a5ac7c.
- `docs/onboarding.md` says `WARP_API_BASE_URL` has a default and that every delivery gets 202. `oz/oz_client.py:43-50` requires it, and `api/webhook.py` returns 400/401/500.
- The retrigger hint says "up to 3 times" (`core/workflows/review_pr.py:803-806`); the limit is 5 per 24 hours (`core/routing.py:119`).
- `docs/` name `core/oz/` and `core/scripts/`, which do not exist. Commit 08e6d86 is titled as a config key; the code is a hardcoded dict.

## 3. Challenges

- **Bash plus files as the runtime.** oz moved to Python on day 6 (f56d0ba) and then to a hosted service. Verdict: local files are fine for flow, wrong for authority. The trust gaps in the brief are the same gap: state the agent can write. Keep local files for the working state, move acceptance and evidence off the checkout. Porting the 1,242-line decision table to Python is reasonable, but it does not fix trust by itself.
- **Tickets as the unit of work.** oz has no ticket files: issue plus PR plus labels. Verdict: partly right. A GitHub issue cannot carry a frozen scope or `Check:` commands, and oz has neither. FW's contract is stronger. Keep it as a contract and let a tracker hold the state. `tracker: github-issues` should be built or deleted.
- **Three risk lanes.** oz has no risk tiers. Its axes are spec versus code and member versus non-member author (`review_pr.py:122-143`, `:1430-1433`). Verdict: FW is right about path risk, but it misses the author axis. oz always requests a human reviewer for its own PRs and opens implementation PRs as drafts (`create_implementation_from_issue.py:497-503`). Add "agent-authored" as an input to the lane.
- **Review limited to changed lines.** oz limits only inline placement; the body is free and the agent has the checkout. Verdict: oz is right. FW's limit reduces noise, but it also hides real defects in unchanged callers. Keep inline binding and add an unbound section that must be judged too.
- **A human accepts every ticket.** oz gates per item by label, adds trusted bypasses, and never freezes the repo: blocking is scoped to one issue or PR. Verdict: oz is right. Drop FW's global write freeze; block only the waiting ticket. INFERRED risk: an issue template that auto-applies `auto-implement` would hand the trigger to anyone. Not checked in spec GH447.
- **Copy-in distribution.** Consumers install a GitHub App and may add one config file and `-local` skills. Skills are referenced as `repo:path` (`core/dispatch.py:76-108`). Verdict: oz shows how few files a project needs, but a service is too heavy for FW and refs here are unpinned. Use an installer that puts framework files under one directory, pinned by version, with `-local` overrides.
- **18 skills.** oz code picks the skill per workflow (`core/workflows/review_pr.py:1401`), and the agent never routes. Verdict: FW's `agentic-route` is redundant where `gate.sh next` can name the skill. Today `gate.sh` names one (`gate.sh:929`).
- **A long `AGENTS.md`.** oz has none. Each run gets a generated prompt with only the step's rules, context and output schema. Verdict: oz is right for automated runs. Interactive tools still need a short file. Generate a per-step brief for all lanes.
- **One hook set for three tools.** oz has no hooks. In-run limits are prompt text only ("Do not run `git fetch`, `gh`", `review_pr.py:1666`); real control is sandbox, token and apply-time checks. Verdict: oz is right that server-side control is what holds, and wrong to rely on prompts. Keep a few hooks as fast feedback, never as evidence.
- **A selftest as the main proof.** oz has a large mocked suite and no agent evals here; the README places evals in a separate product. History prunes test value: 089286e (-718 lines), and 8126cc8 "remove prompt content assertions". Verdict: both lack outcome proof. The lesson for FW: drop tests of prose, and keep behavior tests.

## 4. Delete or simplify

- Delete Mode A as ship evidence. Keep it as a pre-review.
- Delete the `report_sha_ok` no-record pass; it protects nothing in default mode.
- Delete `agentic-route`; let `next` name the skill and brief.
- Shrink `AGENTS.md` to what a per-step brief cannot supply.
- Replace the markdown report parsing (`Head:`, `F1:` regexes) with JSON.
- Delete the test-count ratchet. oz has no equivalent, and FW's rarely runs. Coverage of a changed line is a better idea if one is needed.
- Delete the global `blocked-on-answers` write freeze.
- Delete dead config (`tracker`, `exception_max_days`, unapplied `models.*`) and adopt unknown-key failure.
- Reduce guard regexes that pretend to enforce. Keep the irreversible set and rely on branch protection and CI for the rest.

## 5. Orchestration

- **Plug-in shape.** The repo's main lesson: the agent is a stateless function from context to a typed artifact; everything durable happens outside. FW needs `gate.sh next --json`, `gate.sh result NN --file out.json`, and distinct exit codes for "agent work", "human wait", and "error". Orchestrators can then own dispatch and retries while FW owns legality.
- **Standalone shape.** The same three verbs run locally in a small loop, with the same artifact schema. `critic.command` is then simply one executor.
- **Shared state.** Local state cannot coordinate clones. oz uses GitHub as the durable store plus hidden markers (`oz/helpers.py:234-247`, upsert at `review_pr.py:350-367`). FW's pushed refs already work for numbers; do the same for claims.
- **Asynchrony.** Events arrive late and out of order. Before an irreversible action, re-read live state: `core/cancel_runs.py:181-207`. Handle "still queued" explicitly: 409 retry at `:29-32`.
- **Liveness.** Give every run a max age, a failure path, and a visible status with a link (`core/workflow_adapters.py:182-200`).
- **What oz lacks and FW must add.** Idempotency key from ticket, step and head SHA; a lock on the applier; a claim on the run. See 6.

## 6. Do not copy

- **Fail-open verdict.** Missing or invalid `verdict` becomes `APPROVE` (`review_pr.py:99-119`), and `APPROVE` dismisses earlier blocking Oz reviews (`:1800-1805`). A malformed artifact can clear a block. VERIFIED by reading; test file covers `_parse_verdict`.
- **Silent drop.** `normalize_review_payload` prints and drops invalid comments at apply (`oz/review_validation.py:413-422`), the same flaw as FW `bound_findings`. If all are dropped with an empty body, the result reads "no actionable feedback" (`review_pr.py:1811-1822`).
- **No concurrency protection.** Cron runs each minute with 60s budget, no lock; grep finds none. Overlapping ticks can double-apply (INFERRED). `delivery_id` is only logged and returned, so duplicate deliveries start duplicate runs (VERIFIED by grep).
- **Non-idempotent retry.** A failed apply retries up to 360 ticks (`core/poll_runs.py:40`, `:270-276`), while `create_review` is not guarded. If a step after it raises, the review posts again (INFERRED). Run start precedes `save_run_state` (`core/dispatch.py:215-240`), so a crash orphans a run.
- **Review not bound to a commit.** No `commit_id` on `create_review` (`review_pr.py:1828-1830`), and `synchronize` is not routed (`core/routing.py:441-496`, commit 9d11260). Code pushed after review is not re-reviewed unless asked. FW's `Head:` and reopen-on-change are better here.
- **Soft boundaries.** "ONLY supported way" and "do not call GitHub" are prompts; an implementation run holds push rights (INFERRED).
- **Public sessions by default.** `DEFAULT_SESSION_SHARING_PUBLIC_ACCESS = "VIEWER"` (`oz/oz_client.py:28`), reverted and reapplied (4a93d35, f2caf2e, 08f9f38). Agent transcripts can expose secrets.
- **Unpinned remote skills.** `repo:path` has no ref (`core/dispatch.py:108`), so behavior changes without a commit here.
- **Self-editing loop as shipped.** No caller, so no guard. Commits touching `-local` skills (f7a8794, 3ff6f58, 70cfe4e) are not loop output by their titles, so there is no evidence it improved anything. "Warp Factories" marketing about self-improvement is unsupported here.
- **Weak verification.** `branch_updated_since` checks a committer date (`oz/helpers.py:1185-1203`), which an agent can set. `implementation_summary.md` is required by the skill, but no code reads it (grep shows only a prompt line).
- **Structure.** `oz/helpers.py` is 2,032 lines, `review_pr.py` 1,851. Compat residue remains, e.g. unused `workspace_path`. 12 revert commits, several within a day, show churn in control flow. Vendor lock to Oz and Vercel.
- **Suspicious content.** None aimed at this study. Prompts contain anti-injection rules, as expected for the product.

## 7. If you rebuilt the framework

Keep the decision table, frozen contract, `Check:` commands, risk floors and "scripts own state". Change the trust model: the agent produces typed JSON and never records its own evidence or approval. A runner outside the agent's reach dispatches, collects, validates, and applies, whether that runner is `gate.sh` locally (advisory) or CI and an orchestrator (authoritative). Acceptance and review evidence live in the platform, bound to head SHA. Ship as a pinned directory with `-local` overrides, generate a brief per step, and collect human accept and reject data from the first release.
