# supernovae/SwarmOS: study report

Labels: **[V]** verified by reading code or a harmless check, **[I]** inferred, **[A]** assumed. Nothing from the repo was built or run. Repo paths are relative to `other-solutions/supernovae_SwarmOS/`; `gate.sh` and similar paths are in the framework. License: MIT (`LICENSE`, `MANIFEST.tsv`). Code may be copied with the notice, but it is Go, so for a bash framework every item below is effectively idea-only unless the runtime changes.

## 1. What it really is

- A Go CLI (`swarm`) that **runs the agents itself**: it turns a GitHub Issue into an approved WorkUnit, claims it through a compare-and-swap ref, spawns planner, reviewer, developer and tester in sandboxed snapshots, runs required checks from the approved base, and opens a Draft PR. It never merges. [V]
- Size: 72,607 lines of production Go, 113,716 of tests, 2,140 test functions, 48 Cobra commands. 643 commits between 2026-10-20 and 2026-11-05, 99% by one author. Latest changelog section is v0.9.0. [V] Very young, written at machine speed; 190 of 237 merge commits come from `swarm/issue-*` branches, so it builds itself. [V] That is real dogfood, but no analysis of it exists. [V by search of docs]
- It works as a design: the state machine, fencing and import boundary are real code with adversarial tests. I did not run them. Qualification is narrower than the README suggests: native isolation is Linux/amd64 only, and only Codex has passed a full authenticated WorkUnit. Claude Code and OhMyPi full runs are pending, OpenCode's live run is pending, and the mixed-harness run is unexecuted (`docs/native-qualification.md:9-17`). [V]
- Unsupported claims: "Cryptographically Bound Plan Reviews" (`docs/ARCHITECTURE.md:58`) is SHA-256 equality inside an unsigned JSON blob. `SECURITY.md:112` concedes it "does not cryptographically attest" state. No signing code exists in state handling. [V] "Zero infrastructure" still needs `gh`, Linux, a sandbox runtime and a qualified harness.
- **Key limit:** there is no agent review of code. The reviewer audits `PLAN.md` and `TEST_PLAN.md` before implementation (`.swarm/prompts/reviewer.md`, `internal/workflow/execute_review.go:10-23`). After that come an advisory tester, required checks and a human on GitHub. [V]

## 3. Challenges

- **"The agent does what `gate.sh` prints."** SwarmOS inverts this: the process owns the loop and agents only return files. **SwarmOS is right** for any claim about evidence or unattended use. A prompted agent cannot be its own referee. Keep agent-driven mode for interactive work, labeled self-reported, as `docs/human-led.md` does. Note the limit: `swarm repo validate` in CI does not verify plan approval (`internal/cli/validate.go:165`), so unforgeability stops at the ledger and the human merge. [V]
- **Hooks as the guard layer; one hook set for three tools.** SwarmOS has no hooks. It disables harness hooks, plugins, MCP and subagents, uses a per-harness adapter, probes canaries and fails closed (`SECURITY.md`, `AGENTS.md` invariant 6). **Right on authority, costly in practice:** 11,161 lines of sandbox code, Linux only, chasing harness versions. Do not rebuild this. Rely on the harness sandbox, make hooks an explicit courtesy layer for accidents, and stop presenting them as a boundary.
- **Credentials as the real boundary.** Agents never get GitHub tokens (`AGENTS.md` invariant 5). This is what makes approvals meaningful. **The framework has no equivalent:** the agent shares the human's push rights and `gh` login. Under `trusted-local`, SwarmOS has the same weakness and says so (`SECURITY.md`, "Boundaries that need operator care"). A driver mode must withhold those credentials or its evidence is decorative. [I]
- **Bash plus files.** SwarmOS shows what a typed runtime buys: wrapped errors become exit codes, strict YAML decoding, root-bound file writes. **Partly right.** Its 72k lines are driven by a threat model (open-source forks, hostile contributors) the framework does not need. But flat YAML through awk and `gate.sh` at 1,242 lines will not carry a driver, CAS, JSON and manifests well. [I] Python is already a dependency, or a small single binary; choose one before adding those features.
- **Tickets as in-repo markdown.** SwarmOS splits contract (tracker), state (ref) and code (branch), behind a `Tracker` interface with a local backend (`internal/tracker/tracker.go`). **SwarmOS is right on the split.** A file the agent can edit cannot hold authority. Keep markdown as the offline backend, with `tracker` becoming a real setting.
- **Three risk lanes.** SwarmOS separates the gate (`none|agent|human`, per task) from size, uncertainty and risk, which select prompts and evidence through first-match profiles (`.swarm/config.yaml`). **Split the axes, keep the lanes' best parts.** One tier conflates "who must approve" with "how much process". But the framework's path floors are better than SwarmOS's word lists, and its LOW lane is better too: SwarmOS has no fast path, so a typo pays for the full role pipeline.
- **Review limited to changed lines.** SwarmOS reviews plans, not code. **Both are partly wrong.** Plan review catches scope errors cheaply and gives an approved test plan. Dropping code review leaves defects to tests and humans: 17 "Repair validation" commits exist, and #446, #447 and #451 fixed tests broken by earlier agent PRs. [V] Keep the diff critic, remove the line filter, and add plan review for HIGH only.
- **A human accepts every ticket.** SwarmOS requires an *authorized* approver, and a write-permission bot can approve a task, while `review-human` rejects bot accounts (`internal/tracker/github.go:224`, `:243-247`). **SwarmOS is right.** Separate task approval, plan gate and merge. Policy decides which need a person. The human stays at merge by default.
- **Copy-in.** **SwarmOS is right.** See Take 8.
- **18 skills and a long AGENTS.md.** A generated project gets an 11-line `AGENTS.md` block, four role prompts (191 lines) and a 70-line `SKILLS.md`, compiled per role per task into `SYSTEM_PROMPT.md` (`internal/workspace/worktree.go:790`). The framework has 769 lines of skills an agent must self-select. **SwarmOS is right** when a driver exists, because the process knows the role and needs no routing skill.
- **Selftest as main proof.** SwarmOS has far more tests, names adversarial suites as required checks, and adds env-gated runs against real harnesses (`docs/native-qualification.md`). It has **the same gap**: no eval of outcomes, cost or ceremony value. Worth taking: a harness qualification matrix, since hook protocols drift too.

## 4. Delete or simplify

- `bound_findings` and the changed-line filter; replace with Take 4.
- `test_ratchet` and its local stamp dependency; replace with Take 7.
- The rule that one waiting ticket freezes all product writes. SwarmOS has no global state: everything is per issue and per worktree.
- Manual `status: open` in an agent-writable file as the acceptance mechanism.
- Most of `guard.sh`'s claimed coverage. Keep a short irreversible-actions list and move the rest to Take 9.
- `reviewer-*.sha`: it proves nothing in Mode A.
- Skills: fold into about four role prompts plus a few on-demand procedures once `route` and lane routing live in the script.
- `scripts/` at repo root, dead config (`limits.exception_max_days`, unused `models.*`), and shipped ADRs and `CONTEXT.md`. A generator removes the collision and the leak.

## 5. Orchestration

Standalone: `swarm node run` with watch, concurrency and `--max-jobs` pulls ready issues, and `issue work --next` takes one (`internal/cli/node.go`). [V for flags; loop body skimmed] Plug-in surface: `--json` on most commands, typed exits, `next_action.argv`, `issue work --dry-run` for preflight, `repo doctor`, and separate `claim`, `stage`, `validate` and `submit` verbs an outside scheduler can compose.

What the framework needs, in order: (1) a JSON envelope with `kind`, `status`, `next_action`, and a schema version, which SwarmOS lacks (no `schema_version` in CLI output; only `kind`); (2) separate "work for agent", "wait for human", "failed", "conflict" exit codes; (3) claims with TTL, heartbeat and fencing token on the remote; (4) no global locks; (5) idempotent steps with an explicit "publication unknown" result; (6) a `Tracker` seam; (7) worker capability matching (`RequiredCapabilities`, `NodeProfile`) only if multiple hosts are real. SwarmOS still lacks an event stream, wall-time and cost budgets, and fairness (`todo.md`). Its own note is good discipline: a future central coordinator must not create a second authority (`todo.md:5`).

## 6. Do not copy

- **Scale and density.** `internal/lease/manager.go` is 3,740 lines; `updateArtifact` alone runs about 275. `SECURITY.md` has single bullets of several hundred words. Rules like carry, reapproval and recovery interact in ways that took 643 commits in 17 days to accrete. Nobody can review this at that pace. [I]
- **Default to the weakest ledger.** `repo init` writes `ledger_namespace: hidden` (`internal/harness/templates/swarm/config.yaml`), where rulesets cannot protect refs and any write-access identity can rewrite state (`SECURITY.md:113`). Unsigned state plus unprotected refs undercuts the approval story. If using refs, prefer protected ones, or sign.
- **Hand-curated required checks.** `.swarm/validation/required-checks.yaml` lists test-name regexes and omits most of `internal/cli`, plus `internal/workflow`, `internal/workspace`, `internal/tracker` and `internal/pr`. The full suite runs nightly (`.github/workflows/full-validation.yml:10`). The #451 and #447 titles say tests were "broken by" earlier work, and #446 is a similar fix. [V for lists and titles; I that they reached main] Speed bought with a curated subset let regressions through.
- **Independence off by default.** `security.independent_review` is unset in the repo and in the template, so `checkAgentReviewer` returns early (`manager.go:515-541`). Isolation is real; reviewer independence depends on an optional setting. Make this default on.
- **Fragile text policy.** `plannedDeletions` regex over `PLAN.md` (`import_policy.go:56-71`) and word-list task shaping (`internal/workflow/task_shape.go:33-41`). Their advisory status is right; the patterns are not worth porting.
- **Overbuilding for this framework.** Fork coordinator over comments, OCI, restore helper, dependency proxy (the changelog admits a "dormant" boundary with disabled adapters), storage reclamation.
- **Docs rule against caveats.** `AGENTS.md` section 2 tells agents to avoid "robotic disclaimer chains". The stated intent is honest prose, but it nudges writers away from stating limits, and the "cryptographically" claim shows the risk. [I]
- **Suspicious content:** none found. I grepped for `curl|sh`, `base64 -d`, and "ignore previous". This is not an audit of every file. No instruction in the repo was followed.

## 7. If you rebuilt the framework

Keep the core sentence: scripts own state, one command knows the next legal move, judgment stays in prose. Keep the first-match decision table, Done Contracts, risk floors by path, the LOW lane and the diff critic. Change who holds the loop: a small coordinator (not bash, if it grows past the decision table) runs each role headlessly, and agent-driven mode remains for interactive work with evidence marked self-reported. Move authority out of the agent's reach: contract digest and approval in a remote ref or forge API, claims by CAS with fencing, policy read from the base commit, credentials withheld from workers. Ship as a generator with a hash manifest so the template stays clean, and replace skills with compiled role prompts. Do not build a sandbox, a fork protocol or 72k lines. Add what SwarmOS also lacks: code review with structured findings, and outcome evals built on telemetry.
