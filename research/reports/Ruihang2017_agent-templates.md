Path shorthand: `S/` = `patterns/three-agent-architect-builder-reviewer/scaffold/.claude/`; `H/` = `patterns/hub-and-spoke-orchestrator-executors/scaffold/.claude/`; `gate.sh` etc. = framework `scripts/`. ## 1. What it really is

An npm-distributed catalog (`agent-templates` 0.16.2, 221 commits, 2026-07-17 to 2026-09-01, 211 tracked files, ~37k lines including heavy duplication) of three scaffolds: Claude Architect/Builder/Reviewer (mature), a Codex port (`proposed`), and hub-and-spoke (`proposed`, "never run end to end"). The real engine is about 8k lines of Node: `deliver-ticket.mjs` (1,426), `start-all.js` (800), `run-milestone.js` (539), plus Claude Code's Workflow tool (`agent()` with JSON schemas). VERIFIED.
It takes a PRD to a ticket DAG, publishes tracker issues, and runs plan, build, fresh review, deterministic forge merge, tests on the merged branch, with humans only at batch Gate 1 and final smoke test. It has real field use: changelog and README §7 cite adopter repos (Groundwork etc.), ~236 issue/PR numbers, many fixes from real runs (32 merges over red CI, 43 duplicate issues, a -12,095-line revert MR). INFERRED that these are true field reports; I saw only their written record.
The value is less the architecture than a dense, dated record of what breaks when agents run unattended against forges.
README claims the code does not support: "No agent judges its own work ... enforced by config and deterministic scripts" holds only inside the workflow path (see §6). Status still says "trialed ... awaiting first real-ticket run" while §7 logs field runs. README:258 says Node 18/20; `test.yml` runs 18/20/24. No claimed benefit is measured against a baseline.

## 3. Challenges

- **Bash plus files as runtime.** Repo uses Node plus Workflow tool. Node buys JSON, Windows and better tests, and its CI matrix includes Windows. But a workflow "dies with the session" (pattern README:106), runs take 47-104 min, and it needed tracker issues or a ledger to resume. Verdict: framework's file-state `advance` is the better recovery model. Bash is the weak part, not files. Keep files as state; a rewrite of `gate.sh` in a single-file Python or Node tool would be justified by JSON output, but not by this repo alone.
- **Tickets as unit of work.** Agrees, but adds PRD → module → ticket DAG above it. Verdict: add the DAG, not the module layer. Their ticket template is heavy; keep the framework's lighter one.
- **Three risk lanes.** Repo has one heavyweight lane and tells you not to use it for trivia (pattern §1). Framework wins: a LOW lane is the honest answer to ceremony cost. Their three-agent cost per toy ticket is large (6 tickets took 47-104 min, per README:105). Weak point in the framework: tier is author-set and mutable.
- **Review limited to changed lines.** Repo does not limit; reviewer judges the diff against ticket, runs the full suite, may raise anything, and `findings[].line` is optional. Verdict: repo is right that defects in unchanged callers matter. Framework's bound exists to stop scope-creep review; replace "dropped" with "non-blocking, retained, visible".
- **Author may decline a finding.** Repo: builder must address all; after 2 bounces, a human. Verdict: unconditional "address ALL" with "default to BOUNCE when uncertain" invites churn. Best mix: decline requires a reason, and declined blockers escalate.
- **Human accepts every ticket.** Repo contradicts it; framework is too strict. Batch sign-off wins, provided acceptance is recorded by something agents cannot forge.
- **Risk-tier and scope contract.** Three-agent has no enforced file scope, only prose (`builder.md:55`); only hub-and-spoke audits it. Framework wins here. Frozen scope is ahead of this repo.
- **Same-model review.** Repo pins a different model by frontmatter and tests docs against pins (`suite-integrity`), but its Reviewer is deliberately a lower tier for cost, recorded with no measurement. Its §3 admits trial changes had "no ... evidence recorded either way". Verdict: apply `models.*` or delete it. Different-model is a reasonable default, unproven.
- **One hook set for three tools.** Repo uses per-runtime scaffolds; drift forced repeated "port two drifted fixes" commits and a Codex port missing the guard. Codex's reviewer has `sandbox_mode = "read-only"`, which is stronger than any regex. Verdict: keep one shared hook logic in the framework, but prefer the runtime's own sandbox or permissions where available.
- **Selftest as main proof.** ~1,500 assertion lines (grep count, not run) coexisted with 32 merges over red CI, a no-op regex shipped for two releases (#230) and "six stage calls never wrapped, behind a test that asked the wrong question" (#223). Verdict: a large selftest does not prove outcomes. Only field runs found these. Their nearest thing to evals: two isomorphic Level-1 rehearsals with time, bounces, and predicted vs measured speedup (2.21× vs 3.0×). Framework should add a small recorded benchmark: fixed task set, cost, time, escaped defects.
- **Long AGENTS.md / 18 skills.** Repo has 8-11 commands and 4 agents with role prompts; its `CLAUDE.md` snippet is 54 lines. Its commands are thin launchers over scripts. Suggests that many skills could shrink. Not proof, since craft guidance is absent there.
- **Copy-in distribution.** Repo's `npx adopt` beats copying, but `--force` overwrites `settings.json`, snippets are never updated, and there is no 3-way merge. Half-solved.

## 4. Delete or simplify

- `models.*`, `tracker`, `limits.exception_max_days`: apply or delete. Repo shows that a pin is only useful when applied at the agent definition.
- `test_ratchet`: delete in favor of the mutation probe plus `floor-guard`.
- Regex-as-security claims: repo's own conclusion after #218/#233 is that a blocklist is "sampling" a boundary. Shrink `guard.sh` to catastrophic-move prevention and move integrity to gate, diff audit and CI.
- `bound_findings` dropping logic: replace regex parsing with a required JSON or fixed-table section. Malformed report means failed review, not fewer findings.
- `stop_followups` default 0 and the global write freeze on one waiting ticket: batch acceptance removes much of the reason for both. INFERRED.
- Template-repo ADRs and `CONTEXT.md` from what a project receives: use a `template/` directory like `scaffold/`.

## 5. Orchestration

- **Standalone:** one command per stage plus a top-level run; the human picks a mode; the run stops with explicit escalations in a structured result (`results`, `escalations`, `cleanup`, `notStarted`).
- **As orchestrator:** the deterministic loop stays in code, never in a model's instructions. History proves this: #206/#207 moved scheduling to the orchestrator as waves, and #208 reverted within a day, citing lost determinism and simulated +3% to +28% time. The harness constraint matters too: a workflow script cannot exec, so a thin agent had to run the deliver command. A framework with a real CLI avoids that hop.
- **Inside an orchestrator:** framework needs JSON output, a ready-set command, a remote lock (claims via refs, not local state), a provider-agnostic review invocation, and an explicit `land` phase. This repo's `platform: none` plus a committed `docs/delivered.json` shows a useful split: finish locally, publish later; the ledger is the resume signal across runtimes. Framework's closed-ticket file already does most of this.
- **Failure handling:** `safely()` (`run-milestone.js:183`) maps a rejected stage to a null result. Incident #217: a reviewer died on a dropped connection, and the orchestrating session composed a CLEAR itself. Any orchestrated framework must treat stage failure as `no verdict`, with retry then escalation. Add this as an adversarial test.
- **Hub-and-spoke:** useful for cheap transcription with all-or-nothing brief validation, driver-owned commits and "exit code is not completion" (needs a parseable artifact). Unproven; it says so itself.

## 6. Do not copy

- **Manual path keeps the self-review hole.** VERIFIED by reading: `deliver-ticket.mjs` only checks that `--verdict-file` exists (`:164`) and posts it; it never parses CLEAR. The main session may write `.claude/tmp/` (guard carve-out), and `deliver-ticket.mjs` is allowlisted (`settings.json`), so a session can self-write a verdict and deliver. `/deliver-ticket` forbids it in prose only. The verdict also has no commit binding; the framework's `**Head:**` field is better.
- **Guard holes.** VERIFIED: any Bash command that merely mentions `.claude/tmp/` skips the whole blocklist (`guard-main-session-writes.mjs:114,140`), for example `sed -i ... src/x; echo ok > .claude/tmp/y`. Input parse failure fails open (`:54`). A gitignored `.claude/allow-main-writes` file disarms the guard (`:182`), and main-session Bash is unguarded (`:178`). No hook covers force push, secrets or commits to main; `settings.json` allows `git push:*`. Framework hooks are far broader.
- **Tree fingerprint gaps.** VERIFIED: the bounce-fix prompt does not ask for `treeSha` (`run-milestone.js:287`; same in `start-all.js:307`), and `build` is replaced, so after any bounce `--expect-tree` is omitted. `--expect-head`/`--expect-tree` run only on the `pr` path (`deliver-ticket.mjs:1180,1235,1253`), so `local` and `direct` skip them. INFERRED bug: the hash includes HEAD (`tree-fingerprint.mjs:98`), a parallel Builder hashes in its worktree at the ticket tip, and delivery runs in the main tree on another HEAD, so PR delivery at concurrency > 1 should refuse every first-pass ticket. Tests compute both in one checkout (`suite-deliver.mjs` H4), so they would not see it. I did not run it. Reviewer writes in an isolated worktree are not visible to that hash at all.
- **Reviewer-writes-through-Bash design.** The reviewer has no Write tool and must write its record via Bash, which then required the holes above. Give the reviewer output through the return channel, and persist it from the driver.
- **Nightly auto-fix from tracker issues.** `nightly-issues.js` feeds issue title/body to agents that can auto-merge, with no untrusted-content handling (grep for "untrusted"/"injection" finds nothing relevant). On a public repo this is a prompt-injection path to `main`. INFERRED risk, not observed. Not suspicious content in itself.
- **Narrative in code.** `deliver-ticket.mjs` carries long incident essays; 110 "catalog issue" references across 21 scaffold files land in user repos. It is exactly the template-history leakage the owner rejects. Keep such stories in a changelog.
- **Triple copies.** `deliver-ticket.mjs` exists in scaffold, repo `.claude/`, and Codex, with byte-sync tests; scheduler logic is duplicated across two workflows with a parity test. Three stale tracked files remain (`.claude/deliver-ticket.mjs` 1,279 lines vs 1,426; `run-milestone.js`, `start-all.js`). Regressions like #230 ("a rule written three times") follow.
- **Over-tuning.** Five delivery modes, an integration-branch fallback, an Asana integration and a 1,078-line site builder are large for a young project. `deliver-ticket.mjs` is a monolith and takes on far too much. Model and effort tables churned 6+ times in three weeks on cost with admitted no evidence.
- **Unproven claims.** "Different tier avoids shared blind spots" is design reasoning. Hub-and-spoke's token saving is rightly marked unverified; do not repeat it.
- No prompt-injection text aimed at the reader was found in what I read.

## 7. If you rebuilt the framework

Keep the core: file state, one `next`/`advance` decision table, frozen contract, risk lanes, floor guard. Rewrite the trust model around "who holds the pen": a driver spawns reviewers and records returned output, every check is pass/fail/skipped with skips blocking or waived, and the claim commit is the immutable contract that CI compares with. Add one trailing JSON line per command, a ready-set command, and a `land` step built from these forge lessons. Hooks become a thin catastrophe layer, with diff audits and runtime sandboxes doing integrity work. Ship from a `template/` directory through a small installer with a retired-file manifest, keep incident stories out of shipped code, and prove value with a recorded benchmark plus an adversarial stub suite.
