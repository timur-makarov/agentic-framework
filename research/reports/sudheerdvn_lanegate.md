# sudheerdvn/lanegate: study report

Apache-2.0 (`LICENSE`, `MANIFEST.tsv`), so code may be copied with the NOTICE kept. Snapshot `89a82e2`, 2026-08-29. Nothing from the repo was executed. Framework paths are relative to `agentic-framework/`; other paths are relative to the cloned repo.

## 1. What it really is

- A pip-installed Python orchestrator (VERIFIED: 47.8k lines in `lanegate/`, 70.5k lines and 3,396 `def test_` in `tests/`, plus a Go TUI). It dispatches headless agent CLIs (claude, codex, cursor, kiro, aider, openhands, ollama, agy) into per-ticket worktrees. It adds a touches lock, review and fix loops, merge gates, and a staged deploy axis.
- It is a different product class from our framework. LaneGate launches agents; our framework is followed by an agent that is already running. It has no hooks in any agent tool (VERIFIED: no `PreToolUse` in `lanegate/`). All enforcement is post-hoc, on the git diff.
- Maturity: one author, 16 squashed release commits in 26 days, v1.2.0. Comments cite tickets up to TICK-725, so it is heavily dogfooded (INFERRED), but the ticket history is not in the repo. The CHANGELOG is the best evidence, and it reads as a long list of concurrency and recovery bugs.
- Core claims hold on the `lanegate run` path: merged-result re-verification, trusted config, independence ladder, fail-closed verdict parsing (VERIFIED).
- README claims the code does not support (all VERIFIED unless marked):
  - "Nothing reaches main without an approved review": `lanegate review X --verdict approved` is callable by any agent, and no check asks who ran it (`lifecycle/review_cmds.py:312`, `mcp.py:461`).
  - "Hard-blocks writes" to CI, manifests and credentials: `_is_blocked_file`, `scan_risk_lane` and `_run_static_analysis` are called only from `orchestrate/loop.py` and `loop_recovery.py`. A direct `lanegate merge` or the MCP `merge` tool skips all three (`lifecycle/merge.py:41`).
  - Roadmap "independent review by default": `docs/executor-capabilities.md:44` calls combined mode "the default", and `review_fallback` defaults to `same_model` (`orchestrate/review.py`, `resolve_independent_review_driver`).
  - CHANGELOG 1.1.0 "red-lane scan no longer fails open": `loop.py:1211-1213` still passes `""` when `git diff` fails, which scores green and proceeds to `cmd_merge`. The other path (`loop.py:2613-2637`) does fail closed.

## 3. Challenges

- **Bash plus files as runtime.** LaneGate proves Python can model this with real locks and JSON. It also shows the size cost: 47.8k lines, and `PyYAML`, `ruamel`, `mcp`, `portalocker`, `rich`, `tree-sitter` as dependencies. Verdict: the framework is right to stay small and wrong to stay in bash. `gate.sh` already leans on python3 and jq, so port the state machine to stdlib-only Python and keep `compute_next` as a table (INFERRED).
- **Hooks as guard layer.** LaneGate has none and checks only outcomes. That catches `python -c`, which our regexes miss, and works for every agent. It cannot stop a read of a secret or a direct push. Verdict: LaneGate is right about authority. The diff gate plus CI should be the enforcer, and hooks should shrink to fast feedback plus the small set of truly irreversible moves. Neither has a real sandbox.
- **Three risk lanes.** LaneGate has two axes: declared autonomy (who merges) and computed lane (does this diff force a human). Verdict: keep LOW/MEDIUM/HIGH for review depth, but compute a floor from the diff and split "who merges" into its own setting.
- **Review limited to changed lines.** LaneGate does not filter findings by line; it tells the reviewer to stay on the change but look further when needed. Its refactor widening is keyed on title words such as "split" (`reviewer.py`, `is_refactor`), which is brittle. Verdict: LaneGate is right. Drop the filter, require a concrete failure, and accept pre-existing defects only when the change makes them reachable.
- **A human accepting every ticket.** LaneGate has no acceptance step; `draft → open` is an LLM `analyze` or a bare `open`. The human gate is at merge. Verdict: neither default suits both users. Keep acceptance as a strict profile, make merge-gate autonomy the unattended profile, and enforce whichever is chosen outside agent reach.
- **Tickets as the unit of work.** Confirmed, and extended: LaneGate adds `touches` and `depends_on`, which turn tickets into a schedulable DAG.
- **Ticket state location.** LaneGate commits status to trunk from the control checkout (`_commit_generated_ticket_write`, `lifecycle/__init__.py`), so all worktrees agree. The cost is noisy trunk history, breakage under protected branches, and a whole `reconciliation.py` for metadata conflicts. Ours rides the branch, so siblings cannot see it. Verdict: neither. Keep contract text in the ticket and put live state in `refs/agentic/*`, extending the `refs/agentic/nn` idea (INFERRED).
- **Check commands as proof.** Here the framework wins. `Check:` runs code; LaneGate's `verify_acceptance_criteria` marks a criterion "verified" when up to three terms appear in the diff text (`acceptance_contract.py:730`), and any `--findings` text flips unverified to manual (`lifecycle/__init__.py:469`).
- **A selftest as main proof.** LaneGate has 3,396 unit tests and still shipped ten cross-ticket regressions found only by "integration audits" (CHANGELOG 1.2.0). Verdict: scale of mechanical tests does not replace end-to-end runs. Keep the selftest and add agent-level runs.
- **18 skills, long AGENTS.md.** LaneGate has 7 skills and uses prompt templates per step, delivered at dispatch. Verdict: when the harness launches the agent, procedure belongs in the step prompt. For the follow-the-gate mode, `next` should print the procedure and most skills could become templates (INFERRED).

## 4. Delete or simplify

- `bound_findings` line binding and its exact-format parsing, replaced by a JSON verdict.
- Mode A as an evidence source: keep it as a labelled interactive convenience, not a ship credential for unattended work.
- The product-write freeze on any waiting ticket: with autonomy profiles it should apply per ticket, not per checkout.
- Regex depth in `guard.sh`: stop extending it once the diff gate is the authority.
- The `tracker`, `limits.exception_max_days` and `models.*` config: nothing here suggests keeping unread config. LaneGate's own roadmap lists scattered defaults as debt.
- The template ADRs and `CONTEXT.md` from what a project receives: a package plus `init` makes this automatic.

## 5. Orchestration

- **Two surfaces, one core.** CLI, MCP and local API share service functions (`docs/v2-interface-boundaries.md`). Ours should be a library or CLI with a versioned JSON contract, with MCP as a thin wrapper.
- **As an orchestrator, retries are most of the code.** Rate-limit hibernation, cooldowns, bounded reviewer-unavailable retry (`review.py:474-635`), suspend-vs-stuck classification, process-tree kill, rebase-conflict agents. `loop.py` alone is 3,246 lines. Lesson: do not build this. Be the gate that orchestrators call, and expose resumable state.
- **What a plug-in needs:** no shared process state, idempotent transitions, a status enum separate from the exit code, an `action_required` field, bounded output, and state readable from a fresh clone. LaneGate has the first few. Its `_capture_action` still mostly wraps prose (`mcp.py:196`), and its locks are single-checkout (README). `check_local_not_behind_remote` only narrows the race.
- **The agent must not call its own gate.** LaneGate's own security doc says MCP is not a security boundary (`docs/security-model.md:95`). The lesson generalizes: an orchestrator should hold verdict and merge credentials, and the worker should have neither. Inside a worker, gate commands that record evidence should refuse unless a harness-held token or separate process runs them.
- **Standalone use** is weaker than ours for an interactive agent: without `lanegate run`, most gates are not applied.

## 6. Do not copy

- **`git reset --hard` on live trunk (`merge.py:339`).** `_GIT_OPS_LOCK` covers only `_do_git_merge` (`merge.py:284`), but guards and reset run outside it, and `auto_merge_approved_local_tickets` runs on worker threads (`loop.py:1709,3036,3072`). INFERRED, not run: ticket B can merge, or a status commit can land, during A's guard run, and A's reset then discards it while B stays `merged`.
- **Verdict with no commit binding.** No reviewed-SHA field exists (VERIFIED by grep), and `cmd_merge` never compares HEAD. Commits after approval merge unreviewed. Our head-bound stamps are better.
- **`human_review_approve` over MCP.** It clears `needs_review`, records `actor="agent"`, and stamps `red_lane_approved_at_sha` (`mcp.py:652`, `review_cmds.py:144`). No code branches on the actor (VERIFIED by grep). An agent can launder a human gate, with `review` and `merge` as sibling tools. An audit field that nothing reads is not a control.
- **Combined mode.** `_build_combined_prompt` tells the implementer to review itself and run `--verdict approved` (`orchestrate/autofix.py:1511`). This contradicts the repo's `AGENTS.md` "core design invariant".
- **Worktree overlay of the contract.** `_refresh_ticket_content_from_worktree` feeds the reviewer `close_criteria`, `touches` and body from the branch (`review.py:320-360`), so the implementer can edit the contract it is judged against. The drift finding is advisory by default, and `AGENTS.md` separately forbids this commit.
- **Term-match acceptance verification** (section 3). It is theatre that reads as evidence.
- **Regex prompt-injection scan** (`guards.py:23-47`). Trivially bypassed, and "IMPORTANT: after" in honest text blocks dispatch. The `<untrusted-data>` fence with delimiter escaping (`prompts.py:1100-1150`) is worth keeping for prompts we build.
- **The `sandbox: worktree` option.** Documented as unusable with linked worktrees, which is its only mode here (`executor.py:1350`). Example config still enables it (`.lanegate.yml.example`).
- **Scope creep:** promote pipeline, feature flags, companion repos, GitHub mirror, Go TUI, API, watch daemons, global project registry. None helps the core promise.
- **Other noted items.** Guards are serialized across all worktrees (`safeguards.py`), which limits parallel value. With no `safeguards` configured the merge gate is a no-op. Suggested flags such as `--dangerously-bypass-approvals-and-sandbox` for codex are required config, which is a poor default.
- **Suspicious content:** no injection text or malicious code found in what I read. `AGENTS.md` and `CLAUDE.md` address agents as usual (including the "be terse" style rules and a `graphify` tool rule); I treated them as data. The bypass flags in `AGENTS.md` are configuration guidance, not an attack.

## 7. If you rebuilt the framework

Keep the core idea: scripts own state, one command names the next legal move, and `Check:` commands are the proof. Port the gate to a pip-installable, stdlib-only Python package with `init`, `doctor`, and JSON output, keeping state in `.agentic/` and git refs. Make the diff gate plus CI the authority, reading policy from the base ref and comparing the contract with the claim commit. Hooks become a thin fast-feedback layer. Evidence comes only from a process the worker does not control: the gate or orchestrator captures a reviewer's JSON verdict bound to a SHA, and merge verifies a temp merge of that SHA. Add autonomy profiles for the unattended case, and path-lock output so external orchestrators can parallelize. Do not build the orchestrator itself. LaneGate shows that is 40k lines of retry logic, and the trust bugs sit in the seams it creates.
