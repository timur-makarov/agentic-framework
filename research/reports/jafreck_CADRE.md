# jafreck_CADRE (CADRE, v0.3.1)

Paths without a prefix are in `other-solutions/jafreck_CADRE/`. `fw:` means `agentic-framework/`. License: MIT (`LICENSE`, and `MANIFEST.tsv` row, VERIFIED). All code below may be copied with attribution.

## 1. What it really is

A TypeScript issue-to-PR orchestrator. The `cadre` CLI reads issues from GitHub or Azure DevOps, runs each through 5 fixed phases in its own worktree, spawning `copilot` or `claude -p` as child processes, then opens a PR and optionally merges. 14.9k lines in `src/`, 9.4k in `packages/` (a generic framework with a flow DSL, plus Docker and Kata providers), 14 agent prompts (1,243 lines), 202 test files (61.7k lines). 261 commits, one author, 2026-02-22 to 2026-09-07, almost all before April. VERIFIED.

It is the framework's opposite shape: a **push** runtime that owns the loop, with no hooks, no tickets, no risk tiers. Its best property is that verification runs outside the agent. Its worst is that review never blocks anything. Commit bodies such as `d109e64` (`feat(#65): implement ...`) suggest it was largely built by itself (INFERRED). No outcome data exists. Every "e2e" test mocks git, the shell and the agent (`tests/e2e-pipeline.test.ts:28-60`).

README and doc claims the code does not support (VERIFIED):
- **Container isolation** (`docs/security.md` §1.2, §5). `createProviderRegistry` (`src/platform/provider-loader.ts:27`) has no caller, and nothing in `src/` reads `config.isolation`. Agents always go `AgentLauncher` → `backend.invoke` → `spawnProcess` on the host (`packages/framework/src/runtime/backend/backend.ts:177`) with the full `process.env`, tokens included (`:51`). Commits `7792725`, `29974bf` hardened a path the app never runs.
- **Roster.** `adjudicator` and `integration-checker` are listed but never launched (grep of every `agent:` value in `src/`). Phase 4 is a script, which is better, but gate errors still blame an "integration-checker agent" (`src/core/pipeline/phase-gate.ts:289`).
- **"Verified pull request".** See section 6, items 1-3. A PR can open with blocked sessions and unresolved review findings.
- **"Git operations belong to the runtime"** is a convention. Agents hold Bash and the token; `src/executors/pr-composition-phase-executor.ts:152-155` admits an agent may commit on its own.
- **Dead config:** `dag.verifyDepsBuild` (`src/config/schema.ts:383`), `commits.squashBeforePR` (`:161`). Status `dep-build-broken` is read but never set. `commitPerPhase` history is erased at phase 4 by `git reset --soft` to base (`src/git/commit.ts:182`, `src/core/pipeline/issue-orchestrator.ts:200`).

## 3. Challenges

- **Bash plus files as runtime.** CADRE contradicts it with 24k lines of TypeScript. Framework is right on the core. `compute_next` (`fw:scripts/gate.sh:321`) derives state from git and files, so resume needs no reconciliation. CADRE stores checkpoints and paid for it: at least 12 fix commits on resume and merge state in one week (`a3b32dc`, `4e88e16`, `ec3f8f0`, `98e8fac`, `914164d`, `66a1874`, `730ed0b`, `0e7c3a7`). Derived state beats stored state. Bash remains a limit for glob overlap and JSON, already leaning on python3.
- **Push vs pull.** CADRE owns the loop; the framework answers `next`. For plug-in use, pull wins clearly: another orchestrator can drive `next`/`advance`, but it cannot drive CADRE below whole-issue level. For standalone use, a push loop wins, since nobody has to tell the agent to continue. Verdict: keep the pull core, add a small push driver on top (Take 1). Not one or the other.
- **Hooks as the enforcement layer.** CADRE has none, and relies on running the checks itself after the agent exits. Verdict: post-hoc re-derivation is the stronger half; the framework already does this in CI. CADRE shows what happens with nothing else: `.cadre` leaks needing four layers of cleanup (exclude, unstage, strip, pre-push check). Keep hooks only for irreversible moves and for feedback speed, and stop extending regex coverage. Do not try to close `python -c`.
- **Three risk lanes.** CADRE has none: a one-line fix costs analyst, scout, planner, writer, test-writer, reviewer, whole-PR reviewer and composer, at least 8 invocations. Only `scoutPolicy` and `testable: false` skip anything. Framework is right. CADRE also has no way to demand a human merge for one risky path, since `autoComplete` is global.
- **Review on changed lines only.** CADRE has no bound, and two reviewers: per session and whole PR. Framework's bound correctly stops scope creep, but CADRE's completeness check catches a class it cannot. Keep the bound for defects, add `M1:` (Take 4). A separate per-session reviewer is not worth copying: same model, same material, double cost, no measured gain.
- **Human accepting every ticket.** CADRE's acceptance is batch: a human lists ids or a label query in config (`src/config/schema.ts:133-146`), and that is authorization. Verdict: framework's per-ticket default is right for a local template; the unattended path should be policy, such as `accepted_by: <actor>` from an orchestrator for a labelled issue. Acceptance must stay something the agent cannot set itself.
- **Tickets as the unit.** CADRE treats the tracker issue as the unit and has no file-based contract, so nothing holds `Check:` commands or scope. Framework's contract is the better artifact; plans in CADRE are throwaway. But the identity should allow an external id. Delete the dead `tracker` key, or implement only `--external-id`.
- **18 skills, long AGENTS.md.** CADRE's 14 prompts average under 90 lines because procedure lives in the runtime: each prompt is one job with an input and output contract. Supports moving anything a script sequences out of skills. INFERRED; I did not read the 18 skills.
- **One hook set for three tools.** CADRE has a per-backend adapter that emits frontmatter and CLI args (`agent-file-sync.ts:115+`, `backend.ts`). Comparable; no verdict. Its adapters cover fewer tools with no enforcement at all.
- **Selftest as main proof.** CADRE has far more test volume and the same blind spot. `tests/e2e-workflow.test.ts` asserts strings in a YAML file; template tests assert prompt text. Volume proves nothing about outcomes. Do not grow selftest; spend on an eval harness instead.

## 4. Delete or simplify

- Delete `tracker` from config; CADRE's 1,500 lines of provider code (`src/platform/`) show the real cost of doing it. `gh` is enough.
- Do not add a plan or decomposition layer. CADRE's sessions, steps and sub-tasks need a planner, a parser, a schema, a DAG check and sub-task checkpoints, and the file lists are unenforced. A small ticket is the session.
- Do not add a workflow DSL. `FlowRunner` is 1,554 lines; the issue pipeline is a straight line (`src/core/pipeline/pipeline-topology.ts:48-94`). The framework's first-match table does the same job in less.
- If Take 1 lands, Mode A shrinks to an interactive fallback, and much of the "spawn a subagent" prose in `agentic-critic` can go.
- Reduce `stop_followups` logic to nothing or to a sane default. A driver replaces the stop hook's job in unattended runs.

## 5. Orchestration

As an orchestrator, CADRE shows what the job contains: pick ready work, isolate, spawn, verify, compose PR, merge serially, reconcile. The lessons that survive its own history:
- **Merging is the hard part.** Merges must be serial, because each changes the base (`src/core/merge/pr-completion-queue.ts:50-52,124-129`; rewritten twice, `730ed0b`, `0e7c3a7`). Sequence: try merge, server-side branch update, conflict agent, poll mergeability (`src/core/merge/merge-retry.ts:73-135`). Leave this to the orchestrator; the framework should only report `pr-open`, `merged`.
- **Expose status and reason as data.** `FleetIssueStatus` has typed terminal reasons such as `dep-merge-conflict`, `budget-exceeded`. The framework's `--json` should do the same, with `human_reason`, `failure_class`, and ready sets.
- **Bound everything by budget, not only by round.** Per-issue and fleet token caps are a real need in unattended use.
- **The framework can be the per-issue layer.** A CADRE-like orchestrator could replace phases 2-5 with `gate.sh`: it would gain scope freeze, tiers, findings accounting, and lose nothing. The reverse is not possible, since CADRE exposes one exit code (`src/index.ts:113`) and JSON only via `report`.
- CADRE gives no help with separate clones: there is no lock anywhere, and two runs of one project share `~/.cadre/<project>/`.

## 6. Do not copy

1. **Review that cannot block.** Reviewer process failed: session continues (`src/executors/implementation-phase-executor.ts:270-276`). Review file missing: skipped (`:279`). Whole-PR failure, missing output or parse error: `verdict: 'skip'` (`:450-479`). Max retries: "continuing to phase 4" (`:495-501`). After `fix-surgeon` nothing re-reviews the session (`:339-345`). `executeWholePrReview` returns void, and `pr-composer` receives no review (`src/executors/pr-composition-phase-executor.ts:70-80`), so the PR does not disclose unresolved findings. The framework's answered-findings ledger is much stronger; keep it.
2. **Partial work ships quietly.** Sessions blocked after retries only stop the run when none completed (`implementation-phase-executor.ts:69`). Gate 3→4 needs only a non-empty diff (`src/core/pipeline/phase-gate.ts:228-256`). A failed `test-writer` is ignored (`implementation-phase-executor.ts:220-223`).
3. **Phase 4 fails open in places.** Lint is handled three ways: excluded from `overallPass` and ignored by the gate (`src/executors/integration-phase-executor.ts:139-157,183`), fatal to phases 3-4 on resume (`:21-37`), and fixed in a separate pre-push loop added later (`231e0a8`). One rule would do. Unconfigured build or test writes `pass: true` (`:180-181`). A failed install is only noted (`:69-80`). Build and test are hard-capped at 300 s (`:89,117`).
4. **Agent-writable baseline.** It lives at `.cadre/baseline-results.json` inside the worktree (`integration-phase-executor.ts:51`) with every agent holding write access, and isn't bound to a commit. Appending a name erases a regression. VERIFIED by reading; not exploited.
5. **Regex failure parsing.** `extractFailures` (`.../commands/parse-failures.ts:9-37`) keeps lines starting `FAIL`, `error:` and similar. Runners that report per file (ASSUMED, Jest-style) would mask a new failure in a file that already failed. Cosmetic stderr needed a follow-up fix (`0993320`).
6. **Parallel sessions in one worktree.** Batches run concurrently in a single worktree (`implementation-phase-executor.ts:52`), each commit does `git add -A` (`src/git/commit.ts:36`), and the session review diff is `HEAD~1..HEAD` (`:307`). So one session's review may see another's work, and partial edits get committed together (INFERRED from the code; I did not run it). Declared `files` are never checked against what changed; the framework's frozen scope is real, CADRE's is a hint.
7. **Unsafe defaults.** The app defaults Copilot to `allowAllTools` and `allowAllPaths` true (`src/config/schema.ts:76-77`) although `41c9a11` is titled "explicit opt-in". Claude gets Bash and all MCP (`:97`). Reviewers get `edit` and `execute` too (`src/git/agent-file-sync.ts:148`) and run in the same worktree, unlike Mode B's throwaway worktree (`fw:scripts/gate.sh:977`). All commits use `--no-verify` (`src/git/commit.ts:54`), skipping the host's hooks.
8. **Prompt injection path.** Issue bodies and PR comments reach full-tool agents with tokens in the environment, and `src/core/review/review-discovery-service.ts:61-75` filters only bots (`!c.isBot`), with no check of author or repo role, and review threads are not filtered by author at all. An outsider's comment on a public repo can become a work plan.
9. **Auto-merge trusts the platform.** `mergePullRequest` calls `pulls.merge` first and only waits on checks if that is refused (`src/platform/github-provider.ts:183-209`). Without branch protection, failing checks would not stop it (INFERRED). Opt-in, at least. Also nothing re-verifies after a server-side branch update.
10. **Budget can be blind.** `parseTokenUsage` falls back to regexes and returns 0 (`backend.ts:77-107`), and 0 records nothing (`issue-budget-guard.ts:37`). With the default Copilot backend in silent mode the budget may never trip (INFERRED; I cannot see that CLI's output).
11. **Two parsers for one field.** Ambiguity gate reads a `## Ambiguities` heading (`phase-gate.ts:386-402`) while the halt check reads JSON (`src/core/pipeline/gate-coordinator.ts:94-117`). Default `haltOnAmbiguity: false` makes both advisory. Review-response marks phases 1-2 complete without running them (`src/core/review-response-orchestrator.ts:140-141`), a workaround for a stored checkpoint.
12. **Framework breadth with no second consumer in the repo.** Kata provider, capability negotiation, gate plugins, event middleware: extension points ahead of need. `b2e7b9d` reverted a whole self-report subsystem, the only attempt here at learning from runs.

No suspicious or injected content found in prompts, `.claude/skills/cadre-release/SKILL.md` (first 25 lines read) or `.github/agents/`.

## 7. If you rebuilt the framework

Keep the derived-state decision table, frozen contract, tiered lanes and answered-findings ledger: CADRE proves by counterexample that these are the valuable parts. Change the shape in three ways. Make the core a versioned installed tool with JSON output, keeping state in the git common dir, so a project carries only config and tickets. Add a thin push driver on the pull core, spawning agents through a two-method backend adapter, so reviewer provenance and unattended mode come from process boundaries and not from prose. Replace count-based ratchets and regex finding parsing with failure-set baselines and schema-checked JSON that fails closed. Leave merge queues, fleets and DSLs to orchestrators.
