# lordaeternus/agent-execution-harness

Paths are relative to the cloned repo unless prefixed `fw:` (the framework). Nothing from the repo was run; "traced" means I followed the code by hand. License: MIT (`LICENSE`, `package.json:5`).

## 1. What it really is

- A single-author npm CLI in TypeScript: 67 commits from 2026-04-28 to 2026-05-29, version 0.17.2, 6,325 lines of `src/`, one runtime dependency (ajv). VERIFIED. Tests are about 170 vitest cases, run in CI on three OSes (`.github/workflows/ci.yml:13-15,26-35`). I did not run them.
- A passive CLI. An agent feeds it a JSON plan and steps a persisted state machine: `start → files declare → task start → verify → claim auto → finish` (`src/core/state-machine.ts:15-24`). State lives in gitignored `.agent-harness/runs/*.json`. It has no hooks, no reviewer, no branches and no commits (`grep` for `PreToolUse`, `critic`, `HEAD` in `src/` finds nothing; `scope-guard.ts:47` only uses `rev-parse --is-inside-work-tree`). VERIFIED.
- The README admits a bad agent can ignore it (README:1222-1226). That honesty is its best property.
- It does its bookkeeping as described, but the proof is much weaker than the marketing. v0.17.2 says "fewer ways to claim success without proof"; a strict-mode gate still passes on an invented hash, and its own test locks that in (section 6).
- "Benchmarks" read hand-written JSON and never run the harness (section 6). There is no evidence of better outcomes. This framework gap stays open.

## 3. Challenges

- **Bash plus files as the runtime: half right.** A pure `src/core` with a thin `src/cli`, JSON Schemas (`schemas/`), library exports (`src/index.ts`) and a three-OS matrix is far easier to test and embed than `gate.sh` with inline python. At similar size it gets types and real schema validation. But "files as state" must stay: fw derives state from git, which survives fresh clones and cannot drift. This repo persists state in gitignored, unsigned JSON that an agent can edit. Its own benchmark edits it directly (`scripts/token-benchmark.mjs:151-159`). Verdict: consider a typed kernel; keep git-derived state.
- **Tickets as the unit of work: framework right for proof, repo right on granularity.** Branch, commit and PR give a real evidence anchor; a run has none. But one intent often needs several ordered steps. Add plan import that creates linked tickets rather than copying "run" state.
- **Three risk lanes: keep them, and add the executor axis.** L1-L3 here barely change the flow: they drive lint rules and file caps (`plan-compiler.ts:13,54-62`). Lanes alone miss who is executing.
- **Review limited to changed lines: no contest.** There is no reviewer at all. Its README concedes not every generated test is meaningful (README:1778). This shows what evidence-only completion leaves open: nothing checks whether the proof means anything. The framework is right to review; this repo cannot inform the changed-lines question.
- **A human accepting every ticket: repo right on the direction, wrong on the bar.** Here plan-lint is the only admission step. Lint as admission enables unattended runs. But its lint is weak (`criteria.length < 18`, `plan-compiler.ts:43`), while fw's already rejects vacuous checks (fw: `scripts/ticket-lint.sh:131-157`). Verdict: auto-accept LOW tickets that pass fw's lint; keep humans for HIGH.
- **Copy-in distribution: repo right.** See the installer in section 2.
- **18 skills and a long AGENTS.md: repo right on procedure.** Its AGENTS template is capped at 900 chars and the runtime doc at 1,200 (`token-budget.mjs:5-7`), because the CLI prints the next command. Fw has 5.9 KB of `AGENTS.md` plus 39.5 KB of `SKILL.md`, yet already has "do what it prints". Procedure prose that repeats `gate.sh` should go. Judgment prose should stay; this repo has almost none, which matches its lack of review. Note the irony: a 64 KB README with 20 "What's New" sections.
- **One hook set for three tools: framework right that enforcement needs hooks.** This repo's `runtime_capabilities` (`src/core/runtime-capabilities.ts:6-25`) only picks serial or parallel dispatch; it enforces nothing. The useful lesson is layering: the CLI must work with no hooks, and hooks are an optional per-tool layer whose real coverage is declared per tool.
- **Selftest as the main proof: neither wins.** Same weakness here, with more unit tests and a benchmark that only looks like an eval.
- **Persisted phase machine versus a derived decision table: framework right.** The explicit `ALLOWED` table is pleasantly readable, but a stored phase can drift from the repo. It also forces ceremony steps (`files declare`, `claim auto`) with no safety value.

## 4. Delete or simplify

- Move procedure out of skills and `AGENTS.md` into `gate.sh` output, then enforce a size cap. INFERRED saving: most of 39.5 KB.
- Ship no template project content. A package plus `init` removes the ADR, `CONTEXT.md` and `verify:` leaks at the root.
- Add a check that every config key and output field is read somewhere. This repo has the same disease as fw's dead config: `stop_after_attempts` is emitted but never enforced (`repair-playbooks.ts:43-44`), `validator_command` is never run (`approved-fixtures.ts:14`), and `execution_profile` never sets the run mode (`schema-validation.ts:135`, `session.ts:25`).
- Do not add from this repo: a claims layer, health scores, codebase memory (`src/core/codebase-memory.ts`, 402 lines), or harnessability. Fw's `map.md` is enough.

## 5. Orchestration

- **Plug-in use.** Worth copying: the JSON envelope, the `command`/`stop_if` shape, stateless dispatch that returns ready task packets, capability input (`max_parallel`, `supports_subagents`), versioned JSON Schemas, and a library entry point. The harness never spawns anything, which keeps it embeddable. That is the right boundary for fw: decide and report, let the orchestrator execute.
- **Standalone use.** `next --exact` shows an agent can be run almost entirely by printed commands, which supports fw's premise. Its "weak mode" points at a real use: strong planner, cheap worker, parent validates the patch.
- **What is missing, so do not expect it here.** One `active-session.json` per checkout (`src/cli/session-store.ts:12-15`), so one run per clone. No locks, and `saveRun` writes three files non-atomically (`artifact-store.ts:33-42`). No shared state across clones. Fw's git-ref number reservation is already ahead. Unattended use needs state in git, not gitignored JSON.

## 6. Do not copy

All VERIFIED by reading unless marked. "Traced" items were not run.

- **Self-applied evidence labels.** `--type`/`--types` are free flags (`verify.ts:23-25`) and policy only matches those strings (`evidence-policy.ts:36-41`). Outside strict mode, `verify --types focused_tests,authz_negative_test --cmd "node --version"` satisfies them. Traced.
- **Forged strict evidence.** `gate pass` needs `--output-ref` and `--sha256`, but only the hash's format is checked (`evidence.ts:20-24`, `state-machine.ts:118-120`). `tests/integration/cli.test.ts:62-67` passes with `"a".repeat(64)` and a log file that does not exist. Fw has a similar self-written-report gap, and this is not the fix.
- **Evidence not tied to code.** Nothing records a commit or tree, so edits after `verify` do not invalidate it. Fw is better here (fw: `scripts/lib.sh:59-64`).
- **Scope guard blind to commits.** It reads only unstaged, staged and untracked files (`scope-guard.ts:49-53`), so committing an out-of-scope edit passes `finish` (traced). The baseline is by file name (`:66-67`), so further edits to an already-dirty file are invisible. Fw compares with the merge-base (fw: `scripts/lib.sh:101-107`). Keep fw's.
- **Failed work can finish as `completed`.** A task with only `.md` files has no required evidence (`task-contract.ts:22`). A failing gate sets it `blocked`, which counts as reconciled (`state-machine.ts:134,155`). `gate_failed` claims verify, and evidence policy is "satisfied", so status becomes `completed` (`:161`). Traced. Also, after a failure on the last task, `verify` suggests `claim auto`, `finish` (`verify.ts:99`) rather than a retry.
- **Tautological claims.** Claims are built from evidence, then checked against that same evidence (`auto-claims.ts:9-47`). `no_product_code_changed` tests an agent-supplied string, not the diff (`claims.ts:26-28`). `contract_preserved` regexes agent-written text (`:24`). This is ceremony and looks like proof.
- **Regex command policy.** Case-insensitive `DROP`, `DELETE`, `UPDATE` (`dangerous-command.ts:2-6`) flag a harmless gate such as `vitest run tests/delete-user.test.ts` (traced). On the `gate` path that sets a terminal `halt` (`state-machine.ts:106-111,22`). It also only sees gate commands, not what the agent runs. Fw's guard has the same class of bypass; do not add more of this.
- **Patch parser.** It reads only `---`/`+++` lines (`patch-intake.ts:49-57`). Pure renames and binary changes have none, so one can pass alongside a legal hunk (traced). Paths with spaces are cut at the first space (`:82`). Use `git apply --numstat -z` and `--summary`.
- **Repair hints.** The schema rule (`required|invalid|must be`) runs before typecheck and test (`repair-playbooks.ts:32-35`), so a test failure containing "invalid" is told to fix JSON. Derive the hint from which gate failed.
- **Approved fixtures.** `owner_approved: true` is a field the agent can write, and only schema is validated (`approved-fixtures.ts:23-29`). The control catalog still lists it as covering agent-generated tests (`control-catalog.ts:63-70`). Unsupported claim.
- **Scores.** Harnessability is mostly file existence (`doctor.ts:106-115`). `coding_discipline` counts as covered if `AGENTS.md` contains a word like "evidence" (`doctor.ts:173`).
- **Fake benchmarks.** `benchmark --mode smoke` reads hand-written fixtures (`src/cli/benchmark.ts:9-13`). `fake-gate-smoke.json` is one literal line. `false_success_rate=0` proves nothing, despite the README saying smoke "fails if false success appears" (README:160). `reduction_pct` compares the tool's verbose path with its compact path using a padded 520-char log (`token-benchmark.mjs:56,192`); it is not agent token usage.
- **Installer flaws.** The AGENTS block never refreshes once present (`init.ts:163`), so upgrades leave old rules. Manifest says `merge` ("update safely") for files `init` actually skips (`install-manifest.ts:10`, `init.ts:146`). There are no config migrations.
- **Hard file caps.** More than 3 files in a task is a lint error (`task-contract.ts:26`, `plan-compiler.ts:42`). That fragments real refactors.
- **Author-stack leaks.** This is fw's template problem again: `templates/stetix/`, `supabase/` rules, a hardcoded Portuguese backlog format (`plan-importer.ts:5-7`), and `docs/linkedin-post.md` published through `files: docs`.
- **Suspicious content: none found** in what I read. `docs/superpowers/plans/...hardening.md:3` addresses agents ("REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development"). It is an ordinary plan header; I treated it as data.

## 7. If you rebuilt the framework

Keep git-derived state, the first-match decision table, claim-time freezing, merge-base scope, the reviewer and fw's Done Contract lint: on trust and evidence, the framework is ahead of this repo. Change the shape in three ways. Ship a versioned package with a small kernel and a dry-run `init`, so a project holds only config, tickets and a capped `AGENTS.md` block. Make the kernel's only contract versioned JSON (`next` returns one exact command plus a stop condition, `frontier` returns runnable tickets with block reasons, and a worker returns JSON plus a patch), with hooks and skills as optional layers. Add file-class → required-command rules and an executor-trust setting, both set by policy and never by agent flags. Treat this repo as a good interface study and a warning about what happens when "evidence" is whatever the agent reports.
