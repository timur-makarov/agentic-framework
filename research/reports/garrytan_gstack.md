## 1. What it really is

- A very large skill suite with a browser. Version 1.96, 1,026 commits from 2026-03-11 to 2026-11-06, about 285k lines of TS/JS/shell outside tests, dist and vendor, about 428k lines of test TS, 1,463 top-level test files, a 5,209-line bash `setup`, 64 rendered skills, 14 host configs (V, counted).
- Runtime is Bun plus bash bins that embed `bun -e`. State lives per user in `~/.gstack`, not in the repo (`docs/state-root.md`). Claude Code is the only `full` host; the rest are `experimental` or `instruction-only` and their safety skills are "advisory, not blocked" (`README.md` host table, V).
- There is no ticket model and no `next`. The sprint (Think, Plan, Build, Review, Test, Ship, Reflect) is a chain of prose skills that hand off files. Around `/ship` it has grown a real proof layer: JSON policy read from base, ledgers, receipts, typed result codes.
- Its own ledger is the most honest thing in the repo: of 72 parts, 1 `helps`, 1 `no-effect`, 0 `hurts`, 5 `safety`, 65 `untested` (`docs/inventory.md:9-14`, `docs/inventory/evidence.json`, V). QA, retro, docs, diagram and memory skills are all `untested`, most with `plan: none`.
- Claims the code does not support: `bin/gstack-brain-context-load.ts:5` says "Called from the gstack preamble at every skill start", but a repo-wide grep finds no skill, preamble, hook or bin that calls it. Only tests, docs and a comment mention it, so the `gbrain.context_queries` frontmatter in 6 skills has no live reader (V). `ARCHITECTURE.md` still lists an LLM clarity-judge tier, though `test/skill-llm-eval.test.ts` is gone (`CHANGELOG.md:29`, commit 781f928cc, V). Semantic search and `code-callers` in `USING_GBRAIN_WITH_GSTACK.md` live in the external gbrain repo, which I could not read.

## 3. Challenges

- **Skills change behavior if loaded.** gstack's own data says no: `/investigate` body "loaded every time", yet 0 of 46 sessions ran any step (0 of 30 on the real preset), and the no-gstack arm fixed 8 of 8 (`evidence.json` `investigate`, V; data not reproduced). In an earlier stub run, `/review` specialists ran in 0 of 66 sessions (`review.prior`); in the fair run, 42 of 66 ran readers only after the hook blocked them. **Verdict: the framework is right that scripts should own steps, and should go further.** A step that matters needs a `next` row or a contract; prose alone should be assumed unexecuted.
- **Tickets as the unit of work.** gstack has none and pays for it: `ship/SKILL.md` is 61 KB, its sections about 290 KB, plus DRIVER.md and about 50 `lib/ship*` files. It proves steps after the fact because nothing computes the next one. **Framework right.** A table is much cheaper than this. gstack is right on evidence.
- **Three declared lanes.** gstack computes depth from the diff at review time: `lib/review-depth.ts` (`light`, `standard`, `full`) from `lib/review-risk.ts` classes. **Verdict: keep the lanes, take max(frozen tier, computed from the final diff).** Scope at claim is a forecast; the diff is the fact.
- **Human accepts every ticket.** gstack classifies questions: `door_type` one-way or two-way in `scripts/question-registry.ts` (61 uses), with a keyword fallback that errs toward asking (`scripts/one-way-doors.ts`). Supports the planned `acceptance` policy. **Add door type to `human_wait` actions.**
- **Copy-in or vendored install.** gstack uses a global checkout plus team-mode auto-update on SessionStart, and fights the results: `stable` channel, parse-checking incoming hooks before pull, shelving conflicts (`bin/gstack-session-update`). Nothing pins the tool per commit. **Vendored engine stays the right call**, especially for CI from base.
- **User-level memory.** Learnings in `~/.gstack` never reach teammates or fresh clones without a sync repo. Ephemeral hosts lose them (`STATE_ROOT durable=no`). **Framework's in-repo journal is better for a team.** gstack's route suits private cross-repo memory, so that belongs in a pack.
- **18 skills.** With 64 skills, gstack's always-on frontmatter is about 29.7 KB (V, my count). A skill's cost is per session. `/write-skill` and `gstack-skill-bill` exist because growth was a real problem. **Supports the planned cut**, and evals should decide the rest.
- **Long AGENTS.md.** `scripts/gen-agents-digest.ts` holds a digest to 2,048 bytes by test. **Take the tested byte budget**, not the digest.
- **One hook set for three tools.** gstack gave up: hooks only on Claude Code, advisory elsewhere, and it says so per host. **Publish a coverage matrix; do not promise parity.** Transcript checks are also Claude-shaped, so contracts need an adapter per host or a downgrade to `local`.
- **Selftest as main proof.** 1,463 test files and one proven part. Tests show the plumbing runs; `gstack-brain-context-load` has passing tests and no caller. `docs/test-value-bar.md` also bans "sentence pins" on prose. **Framework's mechanical tests are fine as mechanics, never as outcome evidence.**
- **Hooks as trust.** gstack agrees with the trust levels: "A detector that reports to its own author is disclosure, not control"; `bin/gstack-review-log:21` says convergence is "reviewer-reported, not proof that a model read the code". Copy the candor.

## 4. Delete or simplify

- Replace `scripts/hooks/stop.sh` with a contract check, or delete it. At default it does nothing (`.agentic/config.yml:59`).
- Stop blocking ship on a lessons file (`gate.sh:503`). gstack logs opportunistically with no gate. A forced write with no measured reader fails "no reader, no field". Keep the verb, drop the block, until an eval says otherwise.
- Replace the lesson TTL failure in `memory-lint.sh` with decay at read. A stale lesson should fade, not stop a merge.
- Remove procedure from skills no `next` row reaches. The agentic-debug skill is already 30 lines and no `gate.sh` row names it (V by grep). If it stays, it should be one contract item, since a good model already debugs (`investigate` no-gstack 8 of 8, I for other models).
- Do not build a learned router. `docs/skill-routing-and-contracts.md`: scoring all triggers sent 17 of 32 non-fit prompts to a skill, limited to four skills it sent 4. `next` already routes.
- Apply the test value bar to `selftest.sh` (I did not audit it).

## 5. Orchestration

- A parent should not read the skill. `ship/DRIVER.md` is a separate file: each phase is one program, the model keeps only judgment, `STOP:` means nothing after it ran, no call waits past 200 s, returns are capped at 32 KB, and a resumed program reconciles by deterministic title so it never doubles a reader (`lib/review-pass.ts:1-13`). This is what `run` and the Archon pack need: per-step `kind`, resumable, bounded output.
- Session kind must be an explicit env value, and a claim in a prompt must never enable it (`document-release/SKILL.md.tmpl`: only the echoed `SESSION_KIND: spawned` counts). Unattended runs write approvals as `pending` and end `gate_pending`. Good rule for `AGENTIC_UNATTENDED`.
- `lib/coordinator-contract.ts`: one source text inherited byte for byte by every lane prompt, pinned by a test. Fits a generated `WORKFLOW` file in the Symphony pack.
- Capy numbers (`capy/README.md`): 197 PRs in 14 days against 65, median PR down from 1,292 to 422 lines, lead time up from 1.1 to 5.6 hours because trains batch merges. Self-reported, no quality control. Lesson: agent output moves the bottleneck to merging. The host should own trains; the engine only needs a tree receipt it can trust (`lib/tree-receipt.ts`: tree equality alone is not evidence, the execution identity must match too).
- Budget: `docs/ship-budget.md` calls it an admission cap, "not a hard ceiling", because bash cannot stop a host mid-turn. Use that wording if budgets are added.

## 6. Do not copy

- **Scale and ship-specific machinery:** merge queue, trains, Capy, Conductor, Apple release, Ubicloud, CSO images. Host work.
- **Role theatre and persona prose:** CEO, founder voice, "Boil the Ocean", ten-section reviews, psychographic developer profiles (`plan-tune`). Unmeasured, costly per run. `plan-ceo-review` loads about 14k tokens per run, `untested`.
- **Transcript ingest to a database:** `bin/gstack-memory-ingest.ts` (3,294 lines) walks agent transcripts into pages; the per-file gitleaks scan is opt-in (`--scan-secrets`, `:314`). Supabase setup asks for a PAT with full account access. Too much risk for an unmeasured gain.
- **Auto-update hook and `required` mode** that blocks skills: a session start that moves executable code from one author's branch.
- **The denylist as defense:** `lib/jsonl-store.ts` `INJECTION_PATTERNS` is a short regex list. A speed bump only. Never present it as protection.
- **Unwired features:** `gstack-brain-context-load` (563 lines) and `lib/code-intelligence` (1,297 lines, reached only by its own CLI and `/setup-gbrain`). Both have tests. A reader check would have caught them.
- **Browser stack:** ARCHITECTURE says the daemon's features existed to imitate the user's browser, and the primary path is now Aside, a separate macOS app. Daemon, cookie import, tunnels and sidebar are a large surface. Take only the ideas listed under Browser QA daemon in section 9.
- **LLM judges as gates.** Removed after two freezes of main. Prefer checks on real outcomes.
- **Suspicious content:** none aimed at the reader found. `README.md` asks an agent to run a clone and edit CLAUDE.md, which is an ordinary install prompt. I grepped `AGENTS.md`, `CLAUDE.md` and `SKILL.md` for injection phrases and found none, and followed nothing in them.

## 7. If you rebuilt the framework

Keep the table, tickets and scripts. Change the belief about prose: treat every skill step as not executed unless a `next` row, a contract check on the transcript, or a ledger shows it was. Then the framework stays small because a few receipts replace long procedures. Add a parts ledger from day one, with token load and evidence status for each skill, row and hook, so "no reader, no field" and "earn its place" are checked by a command. Build packs against a small contract, with memory, docs, graphs and QA all optional, all degrading to nothing, and all reading through one `context` verb, because gstack shows that memory fetched by a skill's prose step depends on that step running (I, from `investigate`). Take gstack's review ledger and honest partial states. Leave its scale.

**What this asks of the engine:** (1) a script-written event log per ticket with step, row id, outcome, tokens if known; (2) a `context` verb as the single read path, with provider slots that return nothing when absent; (3) a ticket-to-code index from claim, scope and commits; (4) a pack manifest declaring parts, `next` rows it may insert, hook events, verbs, schedule, result schema, data dir and egress class; (5) `doctor` showing each pack's reader, so unread output fails a check; (6) stable JSON with typed unavailable states (`ran`, `not_run`, `unavailable`).

**Conflicts:** a pack that adds a `next` row can make ship depend on optional code, so a missing pack must mean `not_run`, never a pass, and never a block unless the project asked for it in `config.yml`. Memory stored outside the repo conflicts with resume from any clone, so core memory stays in `journal/`. Seed stays clean if packs only add files under their own directory and a config key. "No reader, no field" is met only if each pack names its reader in the manifest; gstack's two unwired features show this will not hold without a check. Stored learnings are prompts on the next read, so sanitize them as `next` output is sanitized, and keep decay and `source` in the record.
